SOUND, do not weaken:
Attachments are content-addressed, hashed while streaming, written to .part and published by atomic renameTo (Attachments.kt:66-90). A file under its hash name is complete by construction.
Attachment bytes land BEFORE the rows in the capture path (NotebookShell.kt:2339 then :2347), and both rows go in one transaction (Repository.kt:3303-3331).
Attachments live in filesDir, never cacheDir (Attachments.kt:147). The system cannot evict them.
Import verifies everything before touching the live notebook: version gate, per-frame AEAD with index and finality in the AAD, every CHECKSUMS.txt line, SQLite magic, databaseSha256, and every attachment re-hashed.
Dangling references halt the merge before the transaction opens (Merge.kt:229, MergeApply.kt:108), and conflict_log records both sides.
Migrations run per-step in their own transaction and refuse a database from the future by name (Migrations.kt:199-231). No hard DELETE anywhere in main.
The export payload is a plain portable SQLite file re-encrypted to the person's passphrase, not the device-keyed file (Backup.kt:159-175). Already fixed once; must not regress.
The archive can be opened and inspected, date, counts, version, with nothing written (RestoreFlow.kt:99-125). A real dry run and the seed of a proper test-restore.
allowBackup="false" with dataExtractionRules: no silent cloud copy.

GAP, no version of this exists at all:
No integrity check, ever. No PRAGMA integrity_check on open, no periodic attachment rehash. Corruption is only ever discovered by the library, which currently responds by deleting the file.
No crash-recovery state. .replacing, .arriving and .part are all written and none is ever adopted or swept on startup.
No evidence the backup works. Nothing has ever been restored, verified, or read back on the person's own phone. A restore-into-a-sandbox that reports "this archive opens, and here is what is in it" without touching the live notebook is the missing piece, and RestoreFlow is already 80% of it.
No second copy on the device. One file, one place. A rolling encrypted snapshot in app storage would survive the corruption and the half-restore, and needs no cloud, no account, no nagging.
No free-space check anywhere. No StatFs, no usableSpace. Export needs 2x the archive in cache, restore needs 3x, and all three failure modes present as something other than a full disk.
